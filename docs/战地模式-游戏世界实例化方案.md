# 战地模式 · 专用游戏世界的实例化方案

> 目标环境：Mohist 1.20.1（Forge 47.x + Bukkit API）、TACZ 1.1.8、现有 Battlefield 模组
> 前提：已有一个手工搭建的「模板世界」，需要据此派生出一个**只用于对局**的游戏世界

---

## 一、先明确要解决的是哪一类问题

「基于已有世界复制生成」有两种完全不同的落地形态，成本差一个数量级，必须先选：

| 形态 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **A. 一次性派生** | 把模板复制成 `battlefield`，之后所有对局都在这个世界的不同坐标区进行 | 单地图、单对局、人数 ≤ 32 | 几乎为零；但地图会被打烂且不可逆 |
| **B. 每局实例化** | 每开一局复制一份模板目录 → 加载成独立世界 → 打完卸载删除 | 多地图、多对局并行、需要"每局干净地图" | 复制 IO + 世界加载 + 客户端切维度卡顿 |

**建议路线：先做 A，架构上预留 B。**
理由：A 能在 1~2 天内跑通全链路，且能暴露 90% 的兼容性问题（维度注册、传送、gamerule、TACZ 跨维度表现）；B 只是把 A 的"世界准备"换成"复制 + 加载 + 卸载"，上层玩法逻辑不用改。

下文按 B 的完整形态设计，A 是它的退化特例（实例数恒为 1、永不回收）。

---

## 二、现状评估：当前代码离"多世界"差什么

已经天然正确的部分（不需要动）：

| 机制 | 现状 | 结论 |
|---|---|---|
| 维度级广播 | `BattlefieldNet.sendToAllInLevel()` 用 `PacketDistributor.DIMENSION` | ✅ 天然的实例隔离，A 局的状态包不会漏给 B 局 |
| 音效 / 粒子 | `level.playSound(null, ...)` / `sendParticles` 都按维度过滤 | ✅ 同上 |
| 队伍 / 小队存档 | 已锚定 `server.overworld()`（上一轮修复） | ✅ 跨维度不再丢队伍 |
| 背包快照 | `PlayerSnapshotStore` 同样是全局 SavedData | ✅ |
| 对局计时 | `GameSession.getRemainingTicks()` 用 `level.getGameTime()` | ✅ 每实例独立计时，天然正确 |
| 轰炸 / V1 | `BombardmentManager` 的 key 含 `ServerLevel` | ✅ 多实例不串 |

必须改的部分：

| # | 位置 | 问题 | 改法 |
|---|---|---|---|
| 1 | `BattlefieldGameManager.MATCHES` | `Map<arenaName, MatchContext>`，**一张图只能有一局** | 键改为 `instanceId`（如 `area_alpha#1`），`arena` 变成实例的模板引用 |
| 2 | 全局无 gamerule 初始化 | `grep` 确认全项目没有 `getGameRules()` | 实例世界必须显式设 `keepInventory=true`、`doMobSpawning=false`、`randomTickSpeed=0`、`doWeatherCycle=false`、`doDaylightCycle=false`、`doFireTick=false`、`fallDamage` 按需 |
| 3 | `RespawnBeaconManager.getSquadBeacons()` | 遍历 `getAllLevels()` 做全图 AABB 扫描 | 实例变多后成本线性增长；改为「实例 → 信标 UUID 集合」索引 |
| 4 | `syncNameTagTeams()` | 记分板队伍名后缀是 `arenaId` | 改为 `instanceId`，否则两局同图会共用一个队伍 |
| 5 | `sectors.json` 的 `world` 字段 | 静态写死世界名 | 增加 `template` 字段，`world` 在运行时由实例注入 |
| 6 | `MohistTeleport.resolveWorld()` | 裸名找不到会 `createWorld`（走默认地形生成器） | 实例世界**不能**走这条路——它需要"加载已存在的目录"，不是"生成新地形" |

> ⚠️ 第 6 条特别容易踩：`WorldCreator` 不带 generator 时，CraftBukkit 在**目录已存在**的情况下会加载而不是生成；但目录不存在时会跑默认 `NoiseBasedChunkGenerator`，产出一片随机地形。实例化流程必须保证"复制先于加载"。

## 三、整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  模板层（Template，只读）                                     │
│  worlds/_templates/area_alpha/   ← 手工搭建、预生成、预跑光照  │
│  只允许读取，任何流程都不得写入                                 │
└───────────────────┬─────────────────────────────────────────┘
                    │ 复制（robocopy /MIR，异步）
                    ▼
┌─────────────────────────────────────────────────────────────┐
│  实例层（Instance，可写、可弃）                                │
│  worlds/bf_area_alpha_1/  →  ServerLevel "bf_area_alpha_1"   │
│  生命周期：PREPARING → LOADING → WARMING → RUNNING            │
│            → ENDING → UNLOADING → DELETED                    │
└───────────────────┬─────────────────────────────────────────┘
                    │ 传送 / 状态同步
                    ▼
┌─────────────────────────────────────────────────────────────┐
│  对局层（Match，现有代码）                                     │
│  MatchContext / GameSession / SectorManager / ScoreManager    │
│  只认 instanceId，不关心世界是复制来的还是原生的                 │
└─────────────────────────────────────────────────────────────┘
```

三层之间只有两个契约：
1. 实例层向上暴露 `ServerLevel` + `instanceId`；
2. 模板层对实例层只读。

### 关键数据结构

```java
enum InstanceState { PREPARING, LOADING, WARMING, RUNNING, ENDING, UNLOADING }

record ArenaInstance(
    String instanceId,        // bf_area_alpha_1
    String templateId,        // area_alpha
    ServerLevel level,        // 加载后填充，PREPARING 阶段为 null
    InstanceState state,
    Set<UUID> participants,
    long createdAtTick
) {}
```

`MATCHES` 从 `Map<String, MatchContext>` 变成 `Map<String, MatchContext>`，但键从 `arenaName` 换成 `instanceId`——改动集中在一处，`MatchContext` 内部字段基本不动。

## 四、关键实现模式

### 4.1 模板只读化（最重要的一条纪律）

模板目录要当成"编译产物"对待：

- 模板世界**预生成完毕**（用 Chunky 跑满边界内所有区块）
- 模板世界**预跑一遍光照**（进入一次、飞一圈、`save-all`），让 region 文件里带上 Light 数据
- 模板世界的 `level.dat` 里清空：`Player`、`ServerBrands`、`Weather`、`Time`、`DayTime`
- 模板目录设为**只读**（Windows 上 `attrib +R`，Linux 上 `chmod -R a-w`），从物理上防止误写

> 为什么强调光照：1.20 的区块光照存在 region 文件的 `Light` 段里。如果模板从未被加载过，复制出来的实例首次加载会对每个区块同步算光照——1024 个区块能吃掉好几秒，且是主线程。

### 4.2 复制策略：整目录 > 区域 > 结构

| 粒度 | 实现 | 耗时（512×512 地图） | 适用 |
|---|---|---|---|
| **整目录复制** | `robocopy /MIR` / `cp -a` | 20~40MB，SSD 上 < 1s | ✅ 首选 |
| Region 级增量 | 记录被改区块，只回拷对应 `.mca` | 更快，但要自己解析 region 头 | 地图 > 2000×2000 时再考虑 |
| 结构（schematic） | WorldEdit 粘贴 | 大结构粘贴卡主线程 | 只适合小范围修补 |

整目录复制必须带上的子目录：

```
world/
├── level.dat          ← 要改，不能直接拷
├── region/            ← 必须
├── entities/          ← 必须（否则盔甲架/物品展示框/掉落物丢失）
├── poi/               ← 必须（否则村民床、传送门定位失效）
├── data/              ← 建议（地图数据、raids）
├── advancements/      ← 不要
├── playerdata/        ← 不要（会串档）
├── stats/             ← 不要
├── session.lock       ← 必须删除
└── DIM-1/ DIM1/       ← 如果模板带下界/末地，按需
```

`level.dat` 的必改项：

| 字段 | 值 | 原因 |
|---|---|---|
| `Data.LevelName` | 实例 ID | 否则 Bukkit 世界名与目录名不一致 |
| 删除 `Data.Player` | — | 否则每个进入的玩家会继承模板作者的背包/位置 |
| `Data.GameRules.keepInventory` | `true` | 战场玩家不该掉装备 |
| `Data.GameRules.doMobSpawning` | `false` | 省 tick，且避免怪物干扰 |
| `Data.GameRules.randomTickSpeed` | `0` | 停止随机刻（作物/树叶腐烂），省 CPU |
| `Data.GameRules.doWeatherCycle` | `false` | 固定天气，避免雷暴影响视野 |
| `Data.GameRules.doDaylightCycle` | `false` + 固定 `DayTime` | 保证每局光照一致 |
| `Data.GameRules.doFireTick` | `false` | 爆炸不起火，地图更耐打 |
| `Data.Difficulty` | `PEACEFUL` 或 `NORMAL` | 按是否要自然回血决定 |

> 这些规则**不要**指望 `/gamerule` 命令临时设置——它是 per-level 的，复制出来的新世界会带着模板的旧值。必须在 `level.dat` 里改，或在世界加载后立刻用 `level.getGameRules().getRule(...).set(...)` 覆盖。

### 4.3 生命周期状态机

```
PREPARING  ──异步复制目录──▶ LOADING ──主线程 createWorld──▶ WARMING
                                                              │
                                            预加载出生点区块 ◀──┘
                                                              │
                                                              ▼
                                                          RUNNING
                                                              │
                                              对局结束 ◀──────┘
                                                              │
                                                              ▼
                                                        UNLOADING ──▶ DELETED
```

约束：
- **复制可异步，加载必须主线程**。`Bukkit.createWorld()` 会操作 `MinecraftServer.levels`，不能跨线程。
- **WARMING 阶段**把出生点周围 `view-distance + 2` 的区块用 ticket 钉住（`level.setChunkForced` 或 Forge 的 `ChunkTicketManager`），否则开局瞬间 32 人分散传送到不同出生点会触发上百个区块同步生成。
- **UNLOADING 前必须**：踢出所有玩家 → `level.save(null, true, false)` → `Bukkit.unloadWorld(world, true)` → 确认 `server.getLevel(key) == null` → 再删目录（Windows 上文件句柄未释放会删不掉，需要重试）。

### 4.4 实例池与引用计数

不要"来一局建一个"，而是维护一个池：

```java
// 复用条件：同一模板 + 上一局已结束 + 世界未被删除（保留 UNLOADING 后的"热"实例）
Deque<ArenaInstance> warmPool;   // 已加载、已清场、可直接开下一局
```

对**同一张图连开多局**的场景，"不卸载、只重置"比"卸载再复制"快一个数量级：
- 轻量重置：把玩家全部送回大厅，然后用区域回滚恢复被破坏的方块
- 重量重置：卸载 → 删目录 → 重新复制 → 加载（可靠但慢）

建议先用重量重置保证正确性，等地图稳定了再做轻量重置。

### 4.5 维度切换的收口

客户端切维度会重建 `ClientLevel`（重载区块、重算光照、重载实体），有 1~3 秒白屏/卡顿。

**唯一的正确做法是把切换集中在"开局倒计时"里**：
- `joinBattle` → 传送到实例世界的 `wait` 点（一次切换）
- 倒计时 10 秒正好覆盖客户端加载
- 比赛过程中**绝不跨维度传送**（包括复活、部署、信标）

这意味着：`wait` / `lobby` / 出生点 / 信标**必须全部落在实例世界内**。当前 `sectors.json` 里 `lobby` 和 `wait` 可以指向不同世界，实例化方案下必须强制同世界，否则每次复活都要卡一次。

### 4.6 与现有代码的对接点

```java
// 现状
MatchContext ctx = MATCHES.get(arena.areaName);

// 改后
ArenaInstance inst = INSTANCES.acquire(templateId);   // 复制 + 加载 + 预热
MatchContext ctx = new MatchContext(inst.instanceId(), ctx.arena, inst.level());
MATCHES.put(inst.instanceId(), ctx);
```

`MatchContext.arenaId` 语义从"地图名"变成"实例 ID"，`arena` 仍指向模板配置（出生点坐标、票数、时限都来自模板，不随实例变化）。

## 五、性能

### 5.1 成本模型（512×512 地图，32 人局）

| 阶段 | 耗时 | 瓶颈 |
|---|---|---|
| 目录复制（20~40MB） | 0.3~1s | 磁盘 IO（可异步） |
| `createWorld` 加载 | 0.2~0.5s | 主线程，读 level.dat + 注册维度 |
| 出生点区块预热（~200 chunk） | 1~3s | 主线程，读 region + 光照 |
| 全图预热（1024 chunk） | 5~15s | 主线程，**不建议** |
| 运行时内存占用 | 50~100MB / 实例 | 堆 |

结论：**只预热出生点 + 据点周围**，其余靠玩家移动自然加载，配 `view-distance=8`、`simulation-distance=6`。

### 5.2 必须调的服务器参数

```properties
# server.properties
view-distance=8          # 32 人战场够用；10 以上收益递减、带宽翻倍
simulation-distance=6    # 实体 tick 范围，比 view 小能省一大截
max-tick-time=-1         # 避免世界加载触发 watchdog 强杀
sync-chunk-writes=false  # 显著降低区块保存卡顿（代价：崩溃可能丢最后几秒）
```

```yaml
# bukkit.yml（Mohist 共用）
chunk-gc:
  period-in-ticks: 400   # 默认 600，战场玩家移动频繁，适当加快回收
```

### 5.3 实例数量上限

粗略估算：`3G 堆 ÷ (100MB/实例 + 32人×~30MB 玩家/实体开销) ≈ 2~3 个并行实例`。
超过就要么加内存，要么改成"排队开房"。

### 5.4 TACZ 特有的性能点

- 子弹是实体（`EntityKineticBullet`），32 人同时开火时实体数可达数百；`entity-tracking-range` 里 `other` 建议 ≤ 64，避免远处子弹同步。
- 弹道命中判定是射线检测，与区块加载强相关；**玩家所在区块未加载会导致弹道穿透**——这是实例化世界最容易出现的"手感 bug"，预热阶段要把据点周围压实。

## 六、同步

| 问题 | 影响 | 处理 |
|---|---|---|
| 维度切换重建 `ClientLevel` | 1~3s 卡顿/白屏 | 集中在倒计时；切换前发遮罩（现有 `RespawnDeployScreen` 可复用） |
| 区块下发 | 32 人同时加载，单玩家瞬间 ~400 包 | 预热 + `view-distance=8`；必要时用 `ClientboundLevelChunkWithLightPacket` 的批量发送（Forge 默认已批量） |
| 状态包 | 已降频至 10Hz（上一轮修复） | 保持；多实例只是多几路，总量线性增长 |
| 队伍名牌 | 记分板队伍是**全局**的 | 后缀改 `instanceId`；`Team.Visibility.HIDE_FOR_OTHER_TEAMS` 已能隔离显示 |
| 音效/粒子 | 按维度过滤 | ✅ 天然隔离，无需改 |
| 观战者 | 需要跟随实例 | 观战者必须被传进对应实例世界，否则看不到任何东西 |
| 世界时间 | 每实例独立 `gameTime` | `GameSession` 已按 level 计时，✅ |

一个容易忽略的点：**`syncNameTagTeams()` 每 10 tick 会给每个参与者写记分板**（上一轮已降频）。多实例时这是 `实例数 × 人数` 次写入，32 人 × 3 实例 = 96 次/0.5s，仍在可接受范围，但值得留意。

## 七、兼容性（Mohist 特有）

### 7.1 最大的技术风险：运行时动态维度的注册

Forge 的维度在**服务器启动阶段**由 `LevelStem` 注册表确定；Mohist 的 Bukkit 层允许运行时 `createWorld`，但两者是否完全打通需要实测。

**必须先做的技术验证（半天）：**

```java
// 伪代码：最小验证
World w = Bukkit.createWorld(new WorldCreator("bf_test").environment(Environment.NORMAL));
ServerLevel lvl = ((CraftWorld) w).getHandle();          // 反射或直接调用
System.out.println(lvl.dimension().location());           // 期望 minecraft:bf_test
System.out.println(server.getLevel(lvl.dimension()));     // 期望非 null
// 然后：传送一个玩家进去、放方块、开一枪（TACZ）、卸载世界、重新加载
```

要验证的四个断言：
1. `server.getLevel(key)` 能查到新建的 `ServerLevel`（否则 `SectorConfigLoader.resolveLevel()` 永远走 Bukkit 分支，`teleportTo` 会退化成异步传送）
2. 该世界能被正常 tick（实体、方块实体、红石、TACZ 弹道）
3. `Bukkit.unloadWorld()` 后，`server.getLevel(key)` 返回 null（否则世界对象泄漏，重启后 `levels` 里堆一堆僵尸实例）
4. 卸载后目录能被删除（Windows 文件句柄）

**如果第 1 条不成立**，退路是：不使用动态维度，改为"固定 N 个预注册维度"——启动时在 `datapacks` 里放 N 个 `dimension` json，实例只在其中轮转（每局重置内容，不重建世界）。这条路牺牲灵活性，但兼容性最稳。

### 7.2 其他已知坑

| 项 | 说明 |
|---|---|
| `session.lock` | 复制时必须排除，否则新世界加载报 "world is locked" |
| `level.dat` 版本 | 模板与实例必须同一 MC 版本；跨版本复制会触发 DataFixer 升级，可能丢方块实体 |
| `keepInventory` | per-level，复制来的世界继承模板值，必须覆盖 |
| 世界边界 | `WorldBorder` 存在 `level.dat` 里，模板设过边界会被一起复制——正好可以利用，也可以每局重置 |
| 实体 UUID | 复制会让每个实例里的实体拥有**相同 UUID**；同一时刻只有一个实例加载时无碍，但**两实例同时加载会冲突**（Forge 的 `EntityLookup` 按 UUID 索引） |
| TACZ 枪械数据 | datapack 驱动，与维度无关，✅ |
| 计分板 | server 全局，多实例共用，靠队伍名区分 |
| Mohist 的 Bukkit 世界名 | 见 7.4，不要假设它等于维度路径 |

> **实体 UUID 冲突**这条容易被忽略：如果做"热池"（两个实例同时加载），必须给每个实例的实体重新分配 UUID，而这需要遍历全部 `entities/*.mca` 并重写 NBT——成本不低。**建议：同一模板同时只保留一个已加载实例**，用"卸载再建"代替"热池"。

### 7.3 与现有 mod 的交互

- **TACZ**：枪械/配件/弹道不依赖维度，但 `EntityKineticBullet` 的命中判定依赖区块已加载 → 预热要做实。
- **PlayerSnapshotStore / TeamSavedData**：已锚定 overworld，多实例下正确。
- **MohistTeleport**：实例世界是"裸名"（`bf_area_alpha_1`），会命中 `createWorld` 分支——**必须在调用前保证目录已复制好**，否则会生成随机地形。

### 7.4 世界名解析

上一轮已修复的三级解析（原版别名 → `World#getKey()` → 裸名才创建）在实例化场景下是对的，但要注意：
- 实例名不要带 `:`，否则会被当成维度引用而不允许创建；
- 实例名不要用 `the_nether` / `the_end` 这类容易和原版混淆的名字；
- 建议统一前缀 `bf_`，便于运维识别与清理。

## 八、社区组件评估（限定 Mohist 1.20.1）

Mohist = Forge mod + Bukkit 插件，但**不是 Paper**。选型时三条硬约束：

1. 只用 Paper API 的插件（大量优化类插件）❌ 不可用
2. Fabric 系优化 mod（Lithium / Krypton / C2ME）❌ 不可用
3. 强依赖 NMS 内部结构的插件（部分 WE 分支）⚠️ 随 Mohist 版本漂移

| 类别 | 组件 | 在方案中的角色 | 适用场景 | 取舍 / 风险 | 1.20.1 状态 |
|---|---|---|---|---|---|
| 世界管理 | **Multiverse-Core 4.x** | 加载/卸载/传送/别名 | 一次性派生（形态 A）后挂多个世界 | 不负责复制；与 Forge 维度注册的交互需实测；功能与自研重叠 | Bukkit 插件，通常可用，需实测 |
| 世界管理 | **自研（目录复制 + WorldCreator）** | 每局实例化 | 形态 B | 要自己处理 level.dat 清理、卸载安全、UUID 冲突；但完全可控 | — |
| 地图编辑 | **WorldEdit（Forge 版）** | 模板搭建、`//copy` `//paste`、schematic | 手工造图、局部修补、快速试摆 | 大范围 paste 在主线程，会卡；建议只用于编辑期，不用于运行时 | Forge 1.20.1 有构建 |
| 地图重置 | **FastAsyncWorldEdit** | `//regen`、快速还原 | 单世界内的区域重置 | **Mohist 兼容性差**（依赖 Paper/NMS），不建议作为主路径 | Paper 分支为主，hybrid 需实测 |
| 预生成 | **Chunky（Forge 版）** | 把模板/实例的区块跑满 | 开服前一次性预生成模板 | 只解决"生成"，不解决"光照二次计算"；预生成 + 复制才是最优组合 | Forge 1.20.1 有构建 |
| 性能诊断 | **Spark** | 采样火焰图、TPS/MSPT | 定位 tick 热点、世界加载耗时 | 无副作用，建议常驻 | Forge 1.20.1 有构建 |
| 内存优化 | **FerriteCore** | 压缩方块状态/模型内存 | 多实例常驻、内存吃紧 | 需验证与 Mohist 补丁的兼容；出问题先关它 | Forge 1.20.1 有构建 |
| 启动/内存 | **ModernFix** | 缩短启动、降低常驻内存 | 大型整合包 | 同上，注意与 Mohist 的 mixin 冲突 | Forge 1.20.1 有构建 |
| tick 优化 | **Canary / Pluto** | 实体/红石 tick 优化 | 实体多、红石多 | 战场红石极少，**收益低**；与 Mohist 冲突风险中等，不优先 | 需确认 1.20.1 构建 |
| 客户端渲染 | **Distant Horizons** | 远景 LOD | 大战场视野 | 纯客户端；服务端仍要发数据，**不能替代** view-distance 调优 | 客户端 mod，服务端可不装 |
| 载具（后续） | **Valkyrien Skies 2** | 物理载具 | 坦克/飞机 | 物理计算与区块加载叠加，对实例化世界压力大 | Forge 1.20.1 有构建，需实测 |
| 载具（后续） | **Immersive Vehicles** | 内容型载具 | 车/飞机模型与操控 | 需要内容包，体积大 | Forge 1.20.1 有构建 |
| 载具（后续） | **Superb Warfare** | 军事载具/武器 | 与 TACZ 风格接近 | 与 TACZ 功能重叠，注意武器体系冲突 | Forge 1.20.1 有构建 |
| 权限 | **LuckPerms** | `/bt` 命令权限 | 正式服 | 与方案无耦合 | 跨平台，稳定 |

> 表中"有构建"表示该版本线存在 1.20.1 产物，但**在 Mohist 上的实际表现必须自行验证**——混合端不是官方支持组合，任何依赖 NMS 的组件都要先跑冒烟测试。

### 选型结论

- **必装**：Spark（诊断）。
- **推荐**：Chunky（模板预生成）、WorldEdit Forge（造图工具，仅编辑期）。
- **按需**：FerriteCore / ModernFix（内存吃紧时），Multiverse（只做形态 A 时可选）。
- **不用**：FAWE（Mohist 兼容性风险 > 收益）、Paper 系优化插件、Fabric 系优化 mod。
- **谨慎**：载具类 mod —— 等世界实例化跑稳之后再引入，否则两个变量一起调很难定位问题。

## 九、实施路线

### 阶段 0 · 技术验证（0.5 天，必须先做）

一个最小 demo，验证 7.1 的四个断言。**这一步不通过，整个方案要改走"预注册维度轮转"路线。**

### 阶段 1 · 形态 A：一次性派生（1~2 天）

1. 写 `WorldTemplateService.deriveOnce(templateId, targetName)`：复制目录 → 清理 `level.dat` → 加载 → 设 gamerule
2. `sectors.json` 的 `world` 指向新世界
3. 跑通一局完整对局，验证传送、复活、信标、计分、TACZ 弹道

### 阶段 2 · 形态 B：每局实例化（3~5 天）

1. `ArenaInstance` + 状态机 + `INSTANCES` 注册表
2. `MATCHES` 键改 `instanceId`
3. 生命周期钩子：开局准备、结束回收、崩溃兜底（启动时清理 `bf_*` 残留目录）
4. 队伍名后缀、信标索引跟随实例

### 阶段 3 · 优化（按需）

- 只预热出生点/据点区块
- 重量重置 → 轻量重置（区域回滚）
- 实例池预热（提前复制好下一局的地图目录）

## 十、验收指标

| 指标 | 目标 |
|---|---|
| 单实例准备耗时（复制 + 加载 + 预热） | < 3s |
| 开局 32 人同时进入的 MSPT 峰值 | < 100ms |
| 单实例常驻内存 | < 120MB |
| 一局结束到可开下一局 | < 5s |
| 卸载后 `server.getLevel(key)` | 必须为 null（无泄漏） |
| 启动时残留实例目录 | 0（有则自动清理并告警） |
| 跨维度传送次数（单局内） | 0（除开局一次） |

---

## 十一、一句话结论

**先花半天验证"Mohist 能否在运行时创建/卸载一个可 tick 的 Forge 维度"，这是整个方案的地基；通过后按"模板只读 → 整目录复制 → 主线程加载 → 出生点预热 → 打完卸载删除"五步走，玩法层只需把 `MATCHES` 的键从地图名换成实例 ID；社区组件只留 Spark + Chunky + WorldEdit(编辑期)，重型优化与 FAWE 在混合端风险大于收益。**
