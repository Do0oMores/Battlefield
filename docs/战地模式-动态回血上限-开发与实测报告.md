## 二、实际采用的伤害结算时机

**`LivingDamageEvent`，优先级 `LOWEST`。**

理由（按需求 §4.3 逐条核对）：

| 检查项 | 结论 |
|---|---|
| `LivingHurtEvent` 是否还受后续减伤影响 | **是**。它只是伤害管线的第二站，之后还有 `getDamageAfterArmorAbsorb`（护甲+韧性）、`getDamageAfterMagicAbsorb`（保护附魔/抗性）、再扣吸收盾。拿它的数值算上限会把伤害算多。 |
| `LivingDamageEvent` 是否拿到最终伤害 | **是**。Forge 在 `LivingEntity#hurt` 里，护甲→附魔→吸收盾全部结算完、真正 `setHealth` 之前发布，`getAmount()` 就是要扣的血量。 |
| 是否有其他 Mod/Mixin/自定义伤害系统改最终值 | 本项目除了 `PlayerHealthService` 在 `LivingHurtEvent` 里按 `gunDamageScale` 缩放子弹，没有第二处改伤害的地方。缩放发生在 `LivingDamageEvent` 之前，因此这里拿到的已经是缩放后的真实值。 |
| 事件取消 | `LivingDamageEvent` **不可取消**（`javap` 已核实，只有 `get/setAmount`）。被取消的友伤在 `LivingHurtEvent` 阶段就没了，不会走到这里。 |
| 吸收生命值 | 事件里的 `amount` 已经是扣完吸收盾后的值。实测：20 点护盾 + 30 点伤害 → 血量只掉 10，上限保持 100。 |
| 伤害覆盖（不死图腾等） | 图腾在 `LivingDamageEvent` 之后生效；即使覆盖了伤害，死亡/复活路径也会把状态清掉重来（见第六节）。 |

补充一道保险：`applyDamageToCeiling` 里按「受伤前血量」钳一次损失，`100 血挨 300 点` 只算 100，不会算出负上限。

## 三、`regenCeiling` 的计算与存储

**存储**：`CombatTracker.State.regenCeiling`，和脱战计时、压制值放在同一张 `HashMap<UUID, State>` 里。
内存态、不落盘。`-1` 表示未初始化，首次用到时按当时的最大生命值补上（这样不用在加入对局、切维度、复活等每个入口都记着初始化一次）。

**计算**（每次受伤）：

```
loss       = min(事件伤害, 受伤前血量)          // 溢出伤害不算
recoverable= min(loss, maxRecoverableDamage)    // 这次最多能自然回多少
permanent  = loss - recoverable                 // 永久伤
候选 A     = 旧上限 - permanent                  // 伤害池模型
候选 B     = 剩余血量 + recoverable               // 需求文档给的写法
新上限     = min(旧上限, max(候选A, 候选B), maxHealth)
```

`min(旧上限, …)` 这一层就是「普通伤害不得提高已有上限」的全部实现 —— 场景 C（70 血摔 5 点）靠它挡住。

### ⚠️ 与需求文档公式的偏差（需要你确认）

需求文档写的是 `min(oldRegenCeiling, newHealth + recoverableDamage)`，即只取候选 B。
**在所有「满血挨打」的例子里两者逐字一致**（A/B/C/D/E 五个场景实测与单测都过）。

但玩家**还在回血途中**（血量低于上限）时，只取候选 B 会把「本来能回上来的血」判成永久伤：

> 上限 70、血量 40（刚挨完 60，正在回血），这时踩到营火挨 **1 点**：
> 候选 B = 39 + 1 = **40** → 上限从 70 掉到 40，凭空损失 30 点可恢复额度。

这正好违反需求文档自己写的核心原则「自然回血不能恢复历史上**已经被判定为不可自然恢复**的生命值」，而且会让「边打边踩火」变成刷不回来的惩罚。所以实现里多取了候选 A，实测：

```
满血 100 挨 60  → 血量 40，上限 70
40 血再摔 5     → 血量 35，上限 70   （只取候选 B 会变成 40）
35 血再摔 1     → 血量 34，上限 70
```

如果你要的就是「回血途中再挨一下也照样砍上限」的严格版本，把 `applyDamageToCeiling` 里的
`Math.max(byDamagePool, byRemainingHealth)` 改回 `byRemainingHealth` 即可，一行。

## 四、与现有脱战回血系统的集成位置

只改了一处计算，其余逻辑（脱战判定、6 秒延迟、0.1 秒 1 点、压制、出界不回血）**一行没动**：

```java
// CombatRegenService#tick
double ceiling = cfg.enableRegenCeiling ? TRACKER.regenCeiling(id, maxHealth) : maxHealth;
double cap = Math.min(profile.capFor(maxHealth), ceiling);   // 原来是 profile.capFor(maxHealth)
if (health >= cap - HEALTH_EPSILON) continue;
```

- 两个上限取小：`profile.capFor()` 是兵种/状态档位（`regenMaxHealthFraction`），`ceiling` 是这次伤情。
  两者互不干扰，兵种系统接进来也不会打架。
- 开关关掉时 `ceiling` 直接等于 `maxHealth`，等价于旧行为。
- 没有新增回血任务、没有第二个 tick 循环；回血仍然只由 `tickMatch` 里那一次调用驱动。

## 五、医疗包与其他治疗

新增唯一入口 `PlayerHealthService.healPlayer(player, amount, resetRegenCeiling)`：

| 行为 | 处理 |
|---|---|
| 死亡玩家 | 直接返回 `false`，不复活、不加血 |
| 超过最大生命值 | `min(血量 + amount, maxHealth)`，超出部分丢弃，不做"溢出转护盾" |
| `resetRegenCeiling = true`（完整医疗包 / 管理员满血） | 治疗 + 上限重置为最大生命值 |
| `resetRegenCeiling = false`（普通治疗） | 治疗 + 上限至少抬到治疗后的血量（不抬会出现「治到 90 却卡在 70 不回血」） |
| 返回值 | 是否真的回上了血（满血时调 `true` 也会重置上限，只是返回 `false`） |

**其他来源**（药水、`/heal`、其他模组的治疗）不经过这里，行为是：
它们把血量顶到上限之上时，`ceiling < health`，回血 tick 判定 `health >= cap` 直接跳过 —— 不会倒扣血，也不会自动把上限抬上去。
下次再受伤时按新血量重新收紧。**没有副作用路径会意外把上限刷回满血。**

医疗包物品本身没做（本次范围外）。接入时只需要 `healPlayer(player, 40f, true)` 一行。

## 六、死亡 / 重新部署 / 重连 / 切维度

| 场景 | 处理 | 位置 |
|---|---|---|
| 死亡 | `TRACKER.clear(uuid)`，上限随状态一起丢弃 | `CombatRegenService.onDeath` |
| 复活 / 重新部署 | `markRespawn(uuid, now, maxHealth)`：脱战计时重置 + 压制清零 + **上限回到最大生命值** | `onPlayerRespawn` → `CombatRegenService.onRespawn` |
| 退出对局 / 掉线 | `onLeave` → `clear` | `removeParticipant` |
| 断线重连 | 现有架构里掉线即离局（`removeParticipant`），重连后重新 `bt join` 走的是新一局、满血进场，因此不存在"保留半血 + 刷新上限"的漏洞；即便有残留，`onLoggedIn` 也会清掉 | `onLoggedIn` / `removeParticipant` |
| 切换维度 | 状态按 UUID 存内存，与维度无关 → 不清除 | — |
| 最大生命值变化 | `regenCeiling(id, maxHealth)` 每次读取都会把上限钳进 `[0, maxHealth]`，100 血修饰器被摘掉时上限自动跟着降到 20 | `CombatTracker.regenCeiling` |
| 服务端重启 | `onServerStopped` → `reset()` | 已有 |

## 八、尚需实机验证 / 已知风险

1. **死亡 → 部署复活后的上限初始化**：部署按钮需要鼠标点击 `RedeployScreen`，窗口消息注入驱动不了，
   没有跑通「死一次再复活」的完整链路。代码路径与「离局重进」共用 `onRespawn`，单测覆盖了 `markRespawn` 重置上限。
2. **伤员界面**：本次不含客户端改动，血条的淡红「可回血段」仍按 `regenMaxHealthFraction` 画，
   不反映 `regenCeiling`。挨 60 之后血条会显示 40→100 的淡红，但实际只回到 70 —— **数值上是"骗"的**。
   要修必须给客户端发上限（`PROTOCOL` 5 → 6），超出本次范围。
3. **多人同时受伤的 SQL**：`LivingDamageEvent` 是逐实体事件，多人同时被炸时每人各自结算，没有共享状态，理论上安全，但没有实机压测。
4. **真实枪械伤害下的表现**：本次全部用 `/damage` 驱动。`gunDamageScale` 仍是 1.0，
   步枪单发伤害没有实测回填（与上一轮的已知项相同）。
5. **环境问题（与本次改动无关）**：本机两个客户端同时登录时，Forge 握手经常超时（`lost connection: 连接中断`），
   单独启动一个客户端则稳定。复现率约 50%，原因未定位，只影响验证效率。
