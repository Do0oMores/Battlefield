# 战地模式 · 重新部署界面（Redeploy）设计与实施

> 版本：2026-10-25
> 基线：`master` @ `2fe3c80`
> 结论：**部署界面从"测试用按钮"重做为服务端驱动的战术终端界面，并在 Mohist 实机跑通"阵亡 → 选点 → 服务端校验 → 复活"闭环。**

---

## 一、现状审计（改造前）

### 1.1 工程事实

| 项 | 值 |
|---|---|
| Mod ID / 包根 | `battlefield` / `top.mores.battlefield` |
| 主类 | `Battlefield.java`（`commonSetup` 里 `BattlefieldNet::init`） |
| 客户端初始化 | `client/ClientModEvents`、`BFKeyBinds`（U 键）、`BattlefieldHudOverlay` |
| 对局总控 | `game/BattlefieldGameManager`（状态机 `WAITING → COUNTDOWN → RUNNING → ENDING`） |
| 已实现玩法 | **只有突破模式**（战线 + 据点 + 攻方票数）；征服/突袭/团队死斗均未实现 |
| 死亡与重生 | 原版死亡界面 → `PlayerRespawnEvent` → `onPlayerRespawn` 三级回落（显式选择 → 小队信标 → 主出生点） |
| 装备 | `BackpackBridge` 反射调用 Bukkit `Backpack` 插件按槽位下发配装；预览走 `C2SRequestBackpackPreview` |
| 兵种 | **不存在**（无兵种类、无解锁、无配装存档） |
| 地图 | **不存在**底图/坐标映射；只有据点坐标 + 当前战线的可活动矩形 |
| 载具 | 不存在 |
| 小队 | `SquadManager`（对局内分桶），只用于小队分与信标归属，**没有"以队友为出生点"的服务端逻辑** |
| 网络 | `SimpleChannel`，`PROTOCOL` 常量握手校验，`id++` 顺序注册 |

### 1.2 可直接复用的东西

| 复用点 | 用途 |
|---|---|
| `BattlefieldGameManager.deploy()` 的校验骨架 | 阶段 / 阵营 / 存活 / 配装槽位校验、`BattleTeleport`、`BackpackBridge` |
| `PENDING_SPAWN_INDEX` 的"复活时再解析一次"思路 | 改为 `PENDING_DEPLOY(optionId, bpSlot)`，语义不变但不再依赖索引 |
| `S2CGameStatePacket`（2 tick 一次） | 顶部战局栏的票数 / 阶段 / 剩余时间 / 据点进度，**不重复下发** |
| `S2CSectorAreaPacket` | 地图上的可活动区域（己方/敌方） |
| `BeaconRespawnLogic.collect()` | 小队信标候选点（含是否可站立的判定） |
| `CapturePoint`（owner / progress / 点内人数） | 据点部署点的状态与风险提示 |
| `PacketRateLimiter` | 部署数据刷新限频 |

### 1.3 改造前的具体缺陷

1. `RespawnDeployScreen` 是测试 UI：只有一个配装槽位选择器，`spawnIndex` 硬编码 0，点 DEPLOY 直接把界面关掉再发包。
2. `S2COpenDeployScreenPacket` **只注册、从不发送**，服务端也从不告诉客户端"有哪些出生点"。
3. 客户端无法知道某个点能不能部署，只能"点了试试"。
4. `deploy()` 用 `spawnIndex`（0=基地，1..N=第 N 个信标）间接寻址，客户端与服务端的点位顺序必须靠遍历顺序隐式一致。
5. 失败只发一条 actionbar，界面早已被客户端自己关掉。
6. `onPlayerRespawn` 复活后**不重新下发配装**（只有存活状态部署时才下发）。

## 二、设计

### 2.1 布局（横向军事终端）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 突破 / area_alpha       你的阵营 攻方  战线 S1(1/3)   兵力 阶段 剩余 │ 顶部战局栏
├──────────────┬──────────────────────────────────┬────────────────────┤
│ 部署位置 3处 │            战区示意图             │     士兵配置        │
│ ● 攻方主基地 │   ┌──────────┬──────────┐        │ 兵种：未实装 [保留] │
│ ● 据点 A     │   │ 敌方区域  │ 己方区域  │  ◇A    │ 配装：< 背包1 >     │
│ ● 据点 B     │   └──────────┴──────────┘        │ [ ][ ][ ]          │
│              │        图例：攻方/守方/可部署/不可用 │ 无配装数据          │
├──────────────┴──────────────────────────────────┴────────────────────┤
│ 已选 攻方主基地 [可部署]    服务端将重新校验后执行部署   [返回] [DEPLOY]│ 底部操作栏
└──────────────────────────────────────────────────────────────────────┘
```

- 深色半透明面板 + 四角括号 + 等宽信息层级，不使用原版 `Button`/箱子菜单。
- 所有按钮自绘，含正常 / 悬停 / 按下 / 禁用四态；不可用位置**显示原因**而不是只变灰。
- 文字按像素宽度截断（`DeployTheme.trim`），窄窗口不会画出面板外。

### 2.2 中央战区图

工程里没有美术底图，但**有地图模板**——`config/battlefield/templates/<id>/region` 里的 .mca 已被 `TemplateStore`
在后台线程解析成内存里的区块数据。因此底图可以**由服务端自己烘**，不需要任何外部图片资源：

```
模板区块数据(PalettedContainer)  ──后台线程采样──▶  像素数组  ──ImageIO──▶  PNG
        └─ 每列自上而下找第一个非空气方块，取它的 MapColor（和原版地图同一套配色），
           再按与东侧邻列的高度差做轻微山体阴影
```

- **范围**：所有战线的可活动矩形 + 据点半径，外扩 8 格，再夹到模板边界（只烘"能打的地方"，不烘 96 格边距）。
- **精度**：默认 3 格/像素，最长边 320 像素，超出自动降精度；实测 179x99，耗时 15 ms，PNG 15 KB。
- **成本**：烘焙在独立的 `Battlefield-MapBake` 线程上读只读模板，**不加载世界、不占区块票据、不阻塞主线程**，
  也不影响槽位还原；同一 `mapId`（arena + 模板指纹 + 栅格参数）只算一次，进程内 LRU 缓存 6 张。
- **传输**：`S2CDeployMapPacket` 带 PNG + 世界边界，对局地图就绪时主动发给参与者；
  客户端按 `mapId` 缓存纹理，重连/中途加入的人用 `C2SRequestDeployMap` 补拉，一局最多传一次。
- **对齐**：像素边界与投影用同一套换算（`DeployMapRaster`），标记与地形不会错位；图片按等比缩放贴进地图区。
- **降级**：静态世界（没有模板）或关掉烘焙时，`mapId` 为空，界面回到"坐标投影示意图"并明确标注无底图。

地图容器本身仍是三件事：投影、画标记、命中测试。投影单独在 `DeployMapProjection`，
底图只是容器里多一次 blit——换成手绘卫星图/资源包图片时也不需要改布局与标记逻辑。

- 据点用菱形 + 进度条（左攻右守），部署点用状态色环，选中项有脉冲外环与四向准星，不可用项打叉。
- 底图之上再叠一层独立网格与坐标刻度，避免"有了地形就丢了坐标感"。

### 2.3 模式适配

```java
public interface DeploymentRules {
    String modeId();
    String displayName();
    List<DeploymentTarget> targets(DeploymentContext ctx);   // 纯函数，无 MC 类型
}
```

- `DeploymentRules.Registry` 注册 `breakthrough`（唯一实现），arena 配置新增 `"gameMode": "breakthrough"`；配了未实现的模式会**告警并回落**，而不是静默跑成别的模式。
- `DeploymentContext` 只含基本类型 + `TeamId`：据点快照、信标快照、基地坐标、战线序号。规则因此可被单元测试直接构造。
- 突破模式规则：
  - 主基地恒可用；
  - **只看当前战线**的据点 —— 战线推进后旧据点自动从列表消失，天然满足"阶段切换后旧出生点失效"；
  - 己方控制才可部署；点内有敌人 → `CONTESTED`（仍可部署，标注"交战中·敌 N 人"）；敌方控制 → `UNAVAILABLE` + 原因；
  - 小队信标复用 `BeaconRespawnLogic`，落点被阻挡标为不可用。
- 未实现因此**不提供**的选项：队友个体部署（没有服务端锚点校验逻辑）、载具出生点、兵种/配装准入。宁可不显示，也不做点了没反应的假入口。
- 顶部信息模板按 `modeId` 分派（`DeployHeaderModel`）：突破显示"攻方兵力 / 守方兵力∞ / 阶段 / 剩余"，未知模式只显示通用字段。

### 2.4 网络

| 包 | 方向 | 说明 |
|---|---|---|
| `S2CDeployDataPacket` | S→C | 部署数据 + `showScreen`；替代只注册不发送的 `S2COpenDeployScreenPacket` |
| `C2SRequestDeployData` | C→S | 打开界面 / 定时刷新 / 失败后刷新；无载荷，服务端限频 5 tick |
| `C2SDeployRequest` | C→S | `optionId`（`base` / `point:A` / `beacon:<uuid>`）+ 配装槽位 1..9 |
| `S2CDeployResultPacket` | S→C | 成功/失败 + 原因文案 |

- `BattlefieldNet.PROTOCOL` 由 `"3"` 升到 `"4"`（消息表与 `C2SDeployRequest` 布局都变了）。
- 编码端 clamp、解码端按同一上限读取；选项数量两端都截断到 64，异常数据不会把客户端打掉线。

### 2.5 服务端流程

**阵亡**

1. `LivingDeathEvent`（LOWEST，扣票之后）记录 `DEPLOY_WINDOWS[uuid] = (now+1, now+delay+1)`；
2. 下一 tick 推送一次部署数据（带 `waitTicks`），到 `readyAt` 再推一次放开按钮；
   - 必须是下一 tick：`LivingDeathEvent` 早于 `ClientboundPlayerCombatKillPacket`，当场发包会被原版死亡界面盖住；
3. 玩家在"阵亡等待"期间可以浏览列表，但按钮不可用（服务端权威）。

**部署**

1. 客户端发 `optionId + bpSlot`；
2. 服务端重新校验：在对局中 / 已进场 / 阶段不是 WAITING·ENDING / 非观战 / 战斗中存活禁止 / 阵亡等待已结束 / 10 tick 内不重复；
3. **用当前状态重算一遍可选点**再按 id 匹配 —— 据点易主、信标被摧毁、战线推进都会让旧 id 匹配失败 → "该部署点已失效"；
4. 命中后：
   - 阵亡：记录 `PENDING_DEPLOY(optionId, bpSlot)` → `PlayerList#respawn`（与客户端点"重生"同一条原版路径，事件/维度/背包行为一致）；
   - 存活（准备阶段改落点）：直接 `BattleTeleport` + 设置重生点 + 下发配装；
5. `PlayerRespawnEvent` 里再解析一次，成功后传送 + `BackpackBridge.applyBackpackPreset`（**这是本次补上的缺口**：原先复活后不下发配装）。

**离局/结算**

- `sendClientReset` 现在会额外发一条关闭态部署数据，客户端立即关界面；
- `removeParticipant` / `releaseMatch` / `onServerStopped` 清理 `PENDING_DEPLOY`、`DEPLOY_WINDOWS`、`DEPLOY_REQUEST_TICK`；
- 客户端 `ClientGameState.reset()` 清空部署选择与配装预览缓存。

### 2.6 与 `doImmediateRespawn` 的关系（实机发现）

Mohist 的战场世界开着 `doImmediateRespawn=true`（或登录世界开着），客户端会在**死亡瞬间自动复活**，死亡界面根本不出现，部署界面也就没有插入的机会。

客户端这个开关只来自登录包（`ClientboundLoginPacket.showDeathScreen = !doImmediateRespawn`），但原版提供了运行时同步用的游戏事件。现在：

- 玩家进入对局世界时，服务端发 `ClientboundGameEventPacket(IMMEDIATE_RESPAWN, 0F)` 恢复死亡界面；
- 离场时按所在世界的 `doImmediateRespawn` 还原。

这条修复是本次实机验证才发现的关键前提，**没有它整套部署流程在任何开了该规则的服务器上都不会生效**。

### 4.3 手动验证步骤（需人手 / 双人）

1. 双人各进一边，死亡后在界面里选中"交战中"的据点部署，确认落在点内且提示仍在。
2. 打开界面后让队友把该据点打掉：2 秒内列表应变为"不可用"，点 DEPLOY 应提示"该部署点已失效"且**界面不关闭**。
3. 连点 DEPLOY：第二次应收到"部署请求过于频繁"或直接失败，且 `bt status` 里票数与位置只变一次。
4. 界面打开期间执行 `/bt leave`：界面应立即关闭，且不能再发包部署。
5. 结算阶段（`ENDING`）打开界面：应立即关闭并提示对局已结束。
6. 关掉 `Backpack` 插件后再部署：应正常落地、界面提示"无配装数据"，不崩。
