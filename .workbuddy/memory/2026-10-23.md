## 性能缺陷修复（第一轮）

改了 4 个文件，全部只针对"每 tick 全量"类缺陷，不改玩法语义：

1. `BattlefieldGameManager.sendState()`：据点/票数/阶段文案提到循环外只构建一次；
   小队快照改为按 (阵营,小队号) 缓存（原每人重算 O(P) → O(P²)）；
   排序比较器由 `Comparator.comparing(UUID::toString)`（每次比较都拼 UUID 字符串）
   改为 `ServerPlayer::getScoreboardName`（缓存串）。
2. `syncPeriodicViews()`：状态包 20Hz→10Hz（`STATE_SYNC_INTERVAL_TICKS=2`），
   名牌队伍 20Hz→1Hz（`=10`），阶段切换时强制补发一次（`MatchContext.lastSyncedPhase`）。
3. `enforceFrozenPhaseMovement()`：原每 tick 对每人 `teleportTo` 回拉（640 次/秒）；
   改为仅当漂移 > 0.5 格才回拉。
4. `enforceMovableArea()`：原遍历全服玩家再 `participants.contains` 过滤，
   改为只遍历本局参与者；新增 `participants(ctx)` 助手统一解析在线玩家。
5. `ensureNameTagTeam()`：队伍属性只在创建时写一次；`pruneTeamMembers()` 无变化时提前返回，
   不再每次构造 HashSet 副本。
6. `SectorManager`：在线玩家列表从"每个据点取一次"提到 tick 级取一次。
7. `TaczAmmoCapConfig`：`getOrCreate/set/remove` 不再同步重写整份 JSON，
   改为 `dirty` 标记 + `flushIfDirty()`，由 `AmmoStationCooldownCleaner`（每 100 tick，仅主世界）落盘。

验证：`./gradlew compileJava` BUILD SUCCESSFUL。
注意 —— 本机 gradle.properties 里的 127.0.0.1:7890 代理未启动，且 JDK cacerts 校验
libraries.minecraft.net 失败，编译需附加：
`-Dhttp.proxyHost= -Dhttps.proxyHost= -Dhttp.proxyPort=0 -Dhttps.proxyPort=0 -Dhttp.nonProxyHosts='*' -Dnet.minecraftforge.gradle.check.certs=false -Djavax.net.ssl.trustStoreType=WINDOWS-ROOT`

未处理（需改协议或属玩法重构，留待后续）：
- `BombardmentManager.sendSmokePerViewer` 逐玩家发包，轰炸期间约 480 包/秒
- `V1MissileEntity.spawnTrail` 每 tick 两次 `sendParticles`，30 秒飞行期持续发包

## 性能缺陷修复（第二轮：烟幕与 V1 尾迹）

1. `S2CBombardSmokePacket`：去掉 `r/g/b` 三个 float，改带一个 `ownerTeam` byte；
   客户端用 `ClientGameState.myTeam == ownerTeam` 自行判红蓝（与原服务端逻辑完全等价，
   观战者对观战者发射才算友方）。
2. `BombardmentManager.sendSmokePerViewer`：由"遍历全服玩家逐个 `PLAYER` 发包"
   改为一次 `PacketDistributor.NEAR` 广播（半径 96 格，TargetPoint 第 4 参是**半径本身**，
   已用 Bytecode 确认 `PlayerList.broadcast` 内部再平方）。
   加了三道前置判断：坐标有限性、`getServer()==null`、`level.players().isEmpty()`。
   去掉不再需要的 `owner` UUID 参数（`spawnAreaSmoke` 同步简化）。
   效果：15 秒轰炸从 ~8064 包（32 人）降到 ~252 包，与人数无关。
3. `V1MissileEntity.spawnTrail`：发射间隔 1→2 tick，3 个采样点合并为 1 个中点，
   两种粒子各发 1 次；先 `level.getPlayers(半径 64)` 筛观察者，无人则完全跳过；
   再用 `sendParticles(viewer, type, true, ...)` 逐人下发（`force=true` 内部阈值 512 格，
   已用 Bytecode 确认）。粒子数上调（6/10）保持视觉密度。
   新增 `isFinite(Vec3)` + 位移为 0 的提前返回。
4. `BattlefieldNet.PROTOCOL` "1" → "2"（包体布局已变，旧客户端应在握手阶段被拒）。

验证：`./gradlew compileJava` BUILD SUCCESSFUL。
坑点记录：`ServerLevel` 的逐人粒子方法是 **`sendParticles(ServerPlayer, T, boolean, ...)`**
（同名重载），不是 `sendParticle`。

## 七项系统性问题修复（第三轮）

1. **部署**：`C2SDeployRequest` 只传索引；新增 `BattlefieldGameManager.deploy()` 做全量服务端校验
   （对局归属/阶段/阵营/存活/索引范围），坐标由 arena 配置或小队信标解析。
   阵亡时把索引存进 `PENDING_SPAWN_INDEX`，复活瞬间再解析一次（信标可能已被打掉）。
2. **存档维度解耦**：`TeamSavedData.get()` / `SquadSavedData.get()` 内部锚定 `server.overworld()`，
   调用点零改动；`TeamManager.countTeam()` 去掉 `sp.serverLevel()==level` 过滤。
3. **世界名**：`sectors.json` + `writeDefault()` 的 `minecraft:world` → `minecraft:overworld`；
   `MohistTeleport.resolveWorld()` 改为「Bukkit 名 → World#getKey()」两级匹配并**删除 createWorld 兜底**；
   `teleportTo()` 改为 NMS → Bukkit → 告警取消（不再静默退到 fallback），签名去掉 fallbackLevel 参数。
4. **背包快照**：新增 `game/PlayerSnapshotStore`（SavedData，锚主世界，存 inventory/selected/gamemode）。
   `joinBattle` capture；`leaveBattle`/`finishAndReset` restore；`onLoggedIn` 残留快照补发。
5. **计分隔离**：`resetMatch()` 删除全局 `ScoreManager.reset()`，只保留 `participants.forEach(clearPlayer)`。
6. **包长**：`S2CGameStatePacket.MAX_POINT_ID_LENGTH=8` 两端共用；encode 限长 + clamp；
   `overlayTitle/Sub` 也统一；`SectorConfigLoader.parseSectors` 加载期拒绝超长 id 并 error 日志。
   字节布局未变，**无需再升协议**。
7. **信标复活**：`onPlayerRespawn` 三级优先（显式选择 → `BeaconRespawnLogic.tryAutoRespawn` → 主出生点）；
   `tryAutoRespawn` 按距离排序逐个尝试；`BeaconSpawnCandidate` 增加 `ServerLevel level` 字段。

## 世界解析再评估（Mohist）

用户反馈「用的是 Mohist，createWorld 是能实现的」，据此重新评估根因 B：

- 确认：Mohist 上 `Bukkit.createWorld` 确实会成功。**成功恰恰是危险点**——
  不抛异常、静默注册新世界、写入世界列表，之后每次开服都加载；且 `WorldCreator`
  默认 environment 是 NORMAL，造出来的 `the_nether` 是普通世界而非下界。
  另外 `createWorld` 会在调用线程（主线程）生成出生区块，会卡 tick。
- 不确定：Mohist 的 `CraftWorld#getName()` 到底返回 `world_nether`（CraftBukkit 约定）
  还是维度路径 `the_nether`。这条不靠猜，靠日志验证。
- 根因 A 与核心无关：`minecraft:world` 不是任何已注册维度键，`server.getLevel()` 必为 null。

最终实现（`MohistTeleport.resolveWorld`）改成对两种命名策略都成立：
1. 原版维度先查 `VANILLA_WORLD_ALIASES`（只列正确的 `world_nether` / `world_the_end`，
   故意不列 `the_nether` / `the_end`，避免命中历史 bug 造出的假世界）；
2. 再按 `World#getKey()` 匹配 —— 这条与 Bukkit 显示名无关，是通用兜底；
3. **只有不含命名空间的裸名**才允许 `createWorld`（如 `arena_alpha`），
   带命名空间的一律视为"维度引用"，必须已存在。

这样既保住了"按需建图"能力，又不会把维度 ID 走到创建分支。
验证方式：`sectors.json` 临时写 `minecraft:the_nether` → `/bt reload` → `/bt join`，
看日志是「原版维度未加载」还是直接进下界，并检查根目录有没有多出 `the_nether/`。

## 专用游戏世界的实例化方案（设计文档）

产出 `docs/战地模式-游戏世界实例化方案.md`。

关键结论（供后续实现参考）：
- 建议先做「一次性派生」（单世界），架构上预留「每局实例化」；两者差别只在世界准备阶段。
- 现有代码天然支持多世界：维度广播、音效/粒子、队伍存档（已锚 overworld）、
  `BombardmentManager`（key 含 level）、`GameSession`（用 level.getGameTime）。
- 必须改的 6 处：`MATCHES` 键（arenaName → instanceId，一图只能一局）、
  全局缺 gamerule 初始化、信标全图扫描、名牌队伍后缀、`sectors.json` 加 template 字段、
  实例世界不能走 `MohistTeleport` 的 createWorld 分支。
- P0 技术验证：Mohist 运行时 `Bukkit.createWorld` 得到的 `ServerLevel` 能否被
  `server.getLevel(key)` 查到、能否正常 tick、`unloadWorld` 后能否从 levels 移除、目录能否删除。
  不通过则退回「预注册 N 个维度轮转」。
- 两个隐蔽坑：① 复制会让各实例实体 UUID 相同（同时加载会冲突）→ 同模板只保留一个已加载实例；
  ② `keepInventory` 等 gamerule 是 per-level 且随 level.dat 复制，必须显式覆盖。
- 组件选型：必装 Spark；推荐 Chunky + WorldEdit(仅编辑期)；FAWE 与 Paper 系优化插件在 Mohist 上
  风险大于收益；载具类 mod 等实例化跑稳后再引入。
